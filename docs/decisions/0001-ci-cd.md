# CI/CD for the Python calendar worker

## Context

This repository contains one Python 3.11 command-line worker. It reads football data from
SportScore and either writes an ICS file or mutates configured Google Calendars. It has no browser,
mobile, documentation-site, package-workspace, database, compiled artifact, or publishable package
surface.

## Decision

`CI / required` is the repository's single required validation outcome. It installs the committed
`uv.lock` and `package-lock.json` without resolving dependencies again. Ruff checks Python lint
and formatting, ESLint checks JavaScript and JSON, and Prettier checks JavaScript, Markdown, JSON
and YAML formatting. CI also checks types, compiles
the two Python source modules, runs the deterministic unit and provider-contract tests, and audits
every GitHub Actions workflow. Node.js and npm provide development tooling only; the worker runtime
remains Python. Pull requests receive no repository or production secrets.

Local commits use a Husky pre-commit hook with lint-staged to run ESLint, Prettier and Ruff on
staged files, applying safe fixes and blocking remaining errors. Hook installation is handled by
the npm `prepare` script; CI disables install scripts and runs full checks independently.

The existing `Soccer Match Calendar Sync` workflow remains a separate delivery boundary because it
uses a production credential and changes Google Calendar data. Its twice-daily schedule is retained
because calendar usefulness depends on refreshing provider changes without a source commit. Manual
dispatch remains available for recovery. CI never invokes this delivery.

The sync workflow also accepts a manual `dry_run` input. It fetches the same nine SportScore
targets and generates temporary ICS files without loading production credentials or calling
Google Calendar. This optional live provider check stays outside `CI / required`, so availability
of SportScore does not affect deterministic pull-request validation.

Monthly grouped Dependabot updates are the only new scheduled maintenance input. They are required
to keep the Python and npm locks and GitHub Action commit pins reviewable; their pull requests pass
through the ordinary required check and perform no delivery.

## Explicit non-applicable controls

- There is no build or package-publication step because Python source is executed directly.
- Live SportScore and Google Calendar integration tests are excluded from required CI because they
  depend on external, rate-limited or production services. The required suite uses deterministic
  mocks and contract fixtures instead.
- There are no database schema, migration, browser, native-build, monorepo aggregation, release, or
  deployment controls because the repository owns none of those surfaces.

## Enforcement

`main` is protected in strict mode with `CI / required` as its only required status context,
including for administrators. Keep the same check name when reorganizing validation, and update
this decision whenever the repository adds a runtime, dependency manager, build, test suite,
delivery boundary, or other platform surface.
